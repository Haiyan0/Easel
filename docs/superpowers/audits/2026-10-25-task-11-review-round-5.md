## T11-R5-01（P2）：旧初次历史晚到会清空已完成的新轮

定位：./web/frontend/src/components/ControlApp.tsx 活动会话 effect（约 841–861 行），尤其 851–857 行的 setMessages；对照 finishRun 的快照提交与 removeLocalSendRun（约 686–698 行）。

本轮移除了初次历史在提交前的 sendAtStart 校验，将其移到正文提交之后，且未检查 messageSeq/快照提交时序。允许历史与本地输入独立恢复是合理目标，但初次读取的旧快照不能覆盖后来已成功提交的新快照。

已独立复现：

1. 选择没有历史的会话，捕获其初次 GET messages 的空快照，暂停交付；当前用户已可输入。
2. 用户发送 new-prompt，真实 worker 正常完成；真实 SSE 触发 finishRun，新的 GET 返回用户/助手两条消息。
3. 等待页面显示两条 canonical 消息且“发送中”条目已移除。
4. 放行第一步的旧空快照；同一会话的初次加载 effect 仍将 messages 置为空。

```text
AUDIT_INITIAL_SNAPSHOT_MESSAGES 0
AUDIT_MESSAGES_BEFORE_OLD_INITIAL [用户 new-prompt, 助手 你好]
AUDIT_MESSAGES_AFTER_OLD_INITIAL []
```

独立实际产品回调探针也确认：初次快照含旧轮两条，新终态先提交四条并移除对应 LocalSend，旧初次快照最后将界面回退到两条。其新输入与新回答同时消失，LocalSend 已清理，无法再兜底显示。

这是本轮放宽初次加载提交导致的界面回归，服务端消息仍保留，不能描述为数据库/worker 数据丢失。新初次加载完成后的 sendAtStart 检查仅限制后续连接，无法撤销已经发生的旧正文提交。

### 修复要求

- 初次读取、终态刷新、恢复读取等消息提交必须遵守一致的快照时序/代次，旧快照不得覆盖已提交的较新历史；检查必须发生在正文和相关清理提交之前。
- 保留 R4 的本地待确认条目及失败恢复能力；不能靠禁止全部历史恢复来规避，也不能重新把未知请求伪造成成功、暗中 POST 或写客户端助手消息。
- 新终态已提交并清理 LocalSend 后，迟到的旧初次读取不得清空正文、回退分页窗口或基于旧观察清理新的待确认条目。
- 身份、会话选择和 Run/连接所有权约束保持不变；只修改必要实现及回归，不增加业务范围。

### 最小验收

1. 空初次快照先捕获 → 新 Run 真实完成、终态快照提交、LocalSend 清理 → 旧初次快照交付：用户/助手两条保持。
2. 含旧历史的初次快照采用同一顺序：旧轮和新轮消息数量、顺序正确，无回退/重复；分页窗口与已提交消息一致。
3. 反向交付、恢复 GET 失败、同会话重试以及切会话/切账号场景仍按正确所有权提交；LocalSend 不泄漏、不误删。

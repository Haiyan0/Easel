交付 R3-01c 验证了 502 后保留新输入、用同一个 turnId 重试成功，但没有检查重试之前旧助手回答是否仍可读。R3 返工单已经要求“不永久丢掉 r1 的助手输出”，所以本项仍属同一发送/历史生命周期，没有扩大业务范围。

### 修复要求

- 保持发送代次拒绝旧回调，不能回退为直接放行旧 setMessages，以免重新抹掉新输入。
- 将服务端已提交历史与本地待确认输入正确协调：新请求失败/结果未知时，上一轮已完成回答仍应可读，待确认输入和原 turnId 也必须保留；不要求用户再次执行任务才能恢复只读历史。
- 失败恢复如需读取快照，只走授权的 GET，并带身份、会话、发送代次的提交边界。快照读取也失败时明确显示恢复失败/重试入口，不能伪造空历史或丢掉待确认输入。
- 不把未知接纳伪造成成功/失败，不自动再次 POST；不按正文去重，不误删合法相同输入，不写客户端助手消息覆盖服务端快照。
- 对成功、失败和重试的完整发送生命周期做一次对应检查，保持旧请求不能清掉更新请求的待确认状态；不改服务端 Run 幂等或扩大到非聊天业务。

### 最小验收矩阵

1. r1 真实完成且快照含助手回答；r2 返回明确 4xx，在新输入保护生效后交付 r1 旧快照。上一轮回答可读，新输入仍明确属于失败/待确认请求。
2. r2 真实已接纳但页面收到 502/网络断开，不点击重试；旧回答可读，待确认输入/原 turnId 保留，不暗中重发。
3. 随后手动重试，使用同一 turnId；最终服务端快照顺序正确，没有重复用户/助手记录，合法相同正文不被去重。
4. 失败恢复的 GET 再失败、切会话、切账号及较新请求接管时，旧恢复不能写到新身份/选择或清除较新待确认状态。
5. 已通过的旧历史早于/晚于 202、同 Run 旧 controller、连续 SSE 失败、分页、401 清理及目录选择保护继续通过。
